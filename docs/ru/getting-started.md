# Начало работы

Эта страница проводит через установку fleetdeck, открытие пульта, создание первой карточки доски и подключение её к работающей сессии Claude Code. Веб-интерфейса у пульта пока нет; раздел об открытии пульта говорит ровно то, что отвечает по этому адресу сегодня. Последний раздел, о поле `session`, описывает устройство таким, каким оно существует сегодня, и это та часть, которую стоит прочитать внимательно.

## Установка бинаря

Релиза для скачивания пока нет, поэтому собирать нужно из исходников. `make build` кладёт два бинаря в `bin/`:

- `fleetdeck` — пульт и команда `init`, описанная ниже;
- `fleetdeck-status` — репортёр статусной строки, который Claude Code запускает для каждой сессии.

Держите эти два файла вместе. `fleetdeck init` ищет `fleetdeck-status` в том каталоге, из которого запущен, и записывает найденный путь в настройки Claude Code, так что скопированный без пары бинарь оставит `init` отказавшимся подключать статусную строку. `go install` работает так же, если установить оба пакета: они попадают в один и тот же каталог `bin`:

```bash
go install github.com/kroticw/fleetdeck/cmd/fleetdeck@latest
go install github.com/kroticw/fleetdeck/cmd/fleetdeck-status@latest
```

## Запуск `fleetdeck init`

`fleetdeck init` настраивает четыре вещи и печатает по строке на шаг, включая шаги, от которых отказался, и причину отказа:

- **Файл конфигурации** `~/.config/fleetdeck/config.yaml` записывается, только если файла там нет. Существующая конфигурация читается и остаётся ровно такой, какая есть, вместе с комментариями: это YAML, написанный руками, а перезапись его из структуры выбросила бы каждый комментарий и весь порядок ключей, выбранный автором. В таком случае в выводе стоит `(kept)`.
- **Каталог доски** берётся из конфигурации. На машине, где нет ни конфигурации, ни флага `--board`, доска — это `~/fleetdeck/board`, и именно этот путь записывается в создаваемую конфигурацию. В каталоге доски, которого нет или который пуст, создаётся подкаталог `cards` с одной карточкой-примером внутри — пульт читает карточки из `<board.path>/cards/`, а не из самого каталога доски, и пустая доска для пульта является ошибкой, неотличимой от сломанной. Каталог, в котором уже лежат файлы, не трогается, включая подкаталог `cards`.
- **Статусная строка** подключается записью `statusLine` в `~/.claude/settings.json` — именно этого ключа, всё остальное в файле остаётся как было. Этот шаг останавливают две вещи. `statusLine`, который уже запускает что-то другое, отвергается без `--force`: замена статусной строки, настроенной вами, не решение этой команды. `fleetdeck-status`, которого нет рядом с бинарём `fleetdeck`, отвергается сразу — записанный путь, который не работает, сломал бы статусную строку каждой сессии Claude Code на машине.
- **Launch-агент** записывается в `~/Library/LaunchAgents/dev.fleetdeck.panel.plist`, а его лог — в `~/Library/Logs/fleetdeck.log`. Файл агента по этому пути, написанный не этой командой, отвергается без `--force`.

Отказ одного шага не останавливает остальные, а команда завершается ненулевым кодом, если что-то было пропущено, называя, что она нашла и что записала бы. Второй запуск `init` не меняет ни одного файла: каждый шаг сообщает `(kept)`.

Два случая заканчиваются отказом, а не правкой, и по одной и той же причине — `init` не переписывает файл конфигурации, который создавал не он. Конфигурация, в которой не задан `board.path`, остаётся вам на заполнение; флаг `--board`, указывающий не туда, где стоит настроенная доска, отвергается, а не игнорируется молча.

## Загрузка launch-агента

`init` записывает агента и не загружает его. Запуск программы при каждом входе в систему — это изменение вашей машины, и делать его вам. Команда печатается в конце вывода `init`:

```bash
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/dev.fleetdeck.panel.plist
```

`gui/$(id -u)` — это ваш собственный GUI-домен: агент работает от вашего имени, в вашей сессии входа. `bootstrap` и `bootout` — актуальные подкоманды; `launchctl load` и `unload` ещё работают, но в `man launchctl` числятся среди устаревших.

Агент запускает бинарь `fleetdeck` оттуда, где он лежал в момент запуска `init`, поднимает его при входе в систему, перезапускает, если тот завершился, и направляет оба его потока вывода в `~/Library/Logs/fleetdeck.log`. Отменить это:

```bash
launchctl bootout gui/$(id -u)/dev.fleetdeck.panel
```

После переноса бинаря запустите `fleetdeck init` снова, чтобы записался новый путь, затем выполните bootout и bootstrap для агента заново.

## Открытие пульта

Пульт слушает `http://127.0.0.1:7777` — только петлевой интерфейс, на порту, который задаёт `server.port` (см. [`configuration.md`](configuration.md)). Загрузите launch-агент, чтобы пульт работал с момента входа в систему, либо запустите `fleetdeck` в терминале.

Веб-интерфейса пока нет: браузер по этому адресу получит 404. Отвечает сегодня тот API, которым этот интерфейс будет пользоваться, — `GET /api/snapshot` для состояния всего флота, `GET /ws` для его живого потока и маршруты, которые печатают в сессию и двигают карточку. Обращаться к ним могут только страницы, которые пульт отдал сам: запрос с любым другим `Origin` отвергается кодом 403, а тело запроса не в `application/json` — кодом 415.

Проверить, что пульт поднят:

```bash
curl http://127.0.0.1:7777/api/snapshot
```

## Создание первой карточки

Создание карточки не требует пульта: карточка — это markdown-файл с YAML-фронтматтером, следующий конвенции, описанной в [`board-convention.md`](board-convention.md). Скопируйте карточку-шаблон, заполните фронтматтер и опишите задачу в теле.

## Связывание карточки с сессией

Карточка связывается с работающей сессией через одно поле фронтматтера: `session`. Оркестратор заполняет это поле, когда запускает сессию для карточки, и с этого момента значение `session` в карточке — это идентификатор, по которому пульт (когда он появится) будет находить живое состояние этой сессии на демоне.

## Почему `session` — единственное связующее поле

Устройство fleetdeck держит три источника истины и никогда их не смешивает и не позволяет одному подменять другой:

- Control-сокет демона знает жизнь сессии: работает она, ждёт или исчезла, и что сейчас показывает её экран.
- Транскрипт сессии знает, что сессия делала: её шаги, её вопросы, её ответы на данный момент.
- Файлы доски, хранящиеся в git, знают, что означает задача: её стадию, прогресс, лог и то, как она связана с другой работой.

Ровно одно поле связывает их между собой: `session`, записанное на карточке доски. Ничто другое не пересекает границу между этими тремя источниками. В частности, состояние сессии никогда не копируется в карточку. Оно живёт в демоне и читается оттуда каждый раз, когда нужно, а не записывается в карточку один раз и не оставляется устаревать.

Это важно, потому что в момент, когда состояние сессии копируется в карточку как вторая запись, у флота появляются два ответа на один и тот же вопрос — один живой, в демоне, и один замороженный, на карточке, — и эти два ответа начинают расходиться в ту же секунду, как только реальное состояние сессии меняется. Тогда карточке понадобился бы механизм, чтобы держать себя синхронизированной с демоном, а это именно тот второй источник истины, которого это устройство избегает, удерживая связь в одном поле. Карточка — не место для хранения того, что сессия делает. Это место для хранения того, для чего сессия нужна, и того единственного поля, которое говорит, какая именно это сессия.
