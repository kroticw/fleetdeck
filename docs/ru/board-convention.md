# Конвенция доски

Доска флота — это каталог markdown-файлов, каждый из которых «карточка» для одной задачи, с YAML-фронтматтером сверху и произвольным markdown в теле. Карточки живут в git-репозитории, и пульт коммитит собственные правки в этот репозиторий. Эта страница описывает формат файла, кому что разрешено писать, и два неровных места, о которых стоит знать, прежде чем полагаться на доску: расхождение между тем, что проверяют два разных куска кода, и небольшую, осознанно принятую гонку в том, как пишет пульт.

## Пример карточки

```markdown
---
zone: unplanned
stage: active
progress: 20
session: a1b2c3
repo: fleetdeck
created: 2026-09-10
---

# Add a health check endpoint

## Context

The load balancer needs a lightweight endpoint to confirm the service is up.
See issue #42 for the original request.

## Log

- 2026-09-10: started, reading the existing router setup.
```

## Поля фронтматтера

Поля ниже и допустимые для них значения — это схема, которую проверяет валидатор доски, `plugin/templates/board/scripts/validate_cards.py`. Код на Go, который пульт использует для чтения и записи карточек, проверяет меньшую часть этой схемы; смотрите «Два разных уровня строгости» дальше — там точно указано, в чём эти два расходятся.

| Поле | Тип | Обязательно | Допустимые значения |
| --- | --- | --- | --- |
| `id` | строка | да | постоянный номер карточки: `T-` и не меньше трёх цифр (`T-018`) |
| `zone` | строка | да | одно из `urgent`, `unplanned`, `planned`, `niceToHave` |
| `stage` | строка | да | одно из `new`, `active`, `review`, `done`, `blocked` |
| `progress` | целое число | да | одно из `0`, `10`, `20`, `40`, `60`, `80`, `100` |
| `created` | строка | да | дата в формате `YYYY-MM-DD` |
| `session` | строка | обязательно, если `stage` — `active`, `review`, `done` или `blocked` | от 6 до 12 шестнадцатеричных символов |
| `repo` | строка | нет | любая строка; иначе не проверяется |
| `worktree` | строка | нет | абсолютный путь рабочего дерева, в котором работает агент; пишет агент, читает ревью в пульте |

Валидатор также допускает четыре поля, которые Obsidian способен добавлять сам через собственную панель свойств — `tags`, `aliases`, `cssclasses`, `cssclass` — не считая их неизвестными. Любое другое имя поля отклоняется.

### Номер карточки

`id` — единственный идентификатор, который человек может прочитать с панели, назвать вслух и отдать обратно скрипту, чтобы попасть в тот же файл: именно это делает `scripts/card_path.py` на доске. Он постоянный: `session` — это short id той сессии, которая сейчас ведёт карточку, и он меняется от запуска к запуску, а номер выдаётся один раз при создании карточки, и дальше карточку называют им.

Панель показывает номер везде, где карточка появляется на экране — на карточке в колонке, в открытой карточке рядом с `stage` и `progress` и на кнопке, открывающей карточку сессии в списке сессий, — моноширинной плашкой: именно она и не даёт спутать номер с short id сессии, стоящим рядом.

Номер выдаётся ровно в двух местах, и оба захватывают его одинаково — пустым файлом-маркером `.ids/T-NNN`, созданным через `O_EXCL`: это `scripts/new_card.py` доски и кнопка «новая карточка» в пульте. Один захват, а не два независимых счётчика: карточки заводятся параллельно оператором, оркестратором и самими сессиями, и «взять максимум и прибавить единицу» при двух одновременных заведениях выдаёт один номер двум карточкам. Маркер не удаляется никогда — ни при переименовании карточки, ни когда она уезжает в архив, — поэтому номер нельзя ни освободить, ни переиспользовать.

Карточка без `id` — это карточка, заведённая руками мимо обоих путей либо доставшаяся с доски, которая старше номеров: валидатор такую отвергает, а пульт всё равно читает и показывает её, говоря словами, что номера нет, вместо того чтобы оставить пустое место там, где он был бы. Номера карточкам, заведённым до появления схемы, раздаёт `scripts/backfill_ids.py`. Карточка, чей frontmatter не разбирается, про свой номер не говорит ничего — про него ничего и не известно.

## Межполевые правила

Два правила связывают `stage`, `progress` и `session` друг с другом, и оба обеспечиваются как в коде записи пульта, так и в валидаторе:

- Установка `stage` в `done` требует `progress` `100`. Когда запись пульта переводит карточку в `done`, он ставит оба поля одной записью: progress уходит в те же байты, что и стадия, поэтому на диске карточка не бывает в половинном состоянии. И наоборот, установка `progress` в любое значение, кроме `100`, пока `stage` равен `done`, отклоняется сообщением `cannot set progress to %s while stage is done: the board requires progress 100 at stage done`. Валидатор проверяет то же самое правило и сообщает о нём (по-русски, это единственный язык его вывода) так: `при stage done значение progress обязано быть 100`.
- Установка `stage` в `active`, `review`, `done` или `blocked` требует, чтобы `session` было непустым — пульт отказывает сообщением `cannot set stage to %s while session is empty: the board requires a session at stage %s`. Сообщение валидатора объясняет почему: `при stage {stage} поле session обязано быть заполнено: оно единственное связывает карточку с сессией`.

## Кто что пишет

Доска разделяет права записи по тому, кто пишет:

- Пульт пишет четыре поля: `stage`, `progress`, `session` и `repo`. Его путь записи не принимает никакое другое имя поля — попытка попросить его записать `zone` или `created` отклоняется как незаписываемое поле, с сообщением `field is not writable: <field>`. `session` принимается только как короткий id из 6–12 шестнадцатеричных символов; очистить его нельзя. `repo` — путь от домашнего каталога, рабочая копия, в которой работает запущенный пультом исполнитель; `~/` в начале отбрасывается, а пустой, абсолютный или выходящий за домашний каталог путь отклоняется. Запись может назвать значение, которое ожидает увидеть в поле, и тогда отклоняется с сообщением `the card has moved on since this write was made`, если в карточке уже другое: рука, перетаскивающая карточку, действует по снапшоту возрастом до секунды.
- Тело карточки — её заголовок, раздел контекста и лог — принадлежит агентам, работающим над задачей. Пульт никогда не редактирует тело.
- Поле `session` заполняет тот, кто запускает сессию для карточки, до того как сессии сказали о карточке: оркестратор или пульт, когда карточку бросили в колонку active на доске. Пульт запускает сессию без промпта, вписывает её короткий id в карточку, ставит стадию `active` и только потом отправляет одну строку с путём карточки; агент, которому сказали работать по карточке до того, как в ней появился его id, вписывает своё значение поля сам.
- `created` и `zone` пульт после создания карточки не пишет, и они не документированы как принадлежащие агенту тоже. На практике они выставляются один раз, тем, кто создаёт карточку, и дальше не трогаются. `repo` выставляется так же, и пульт пишет его ещё и по просьбе из открытой карточки.
- `worktree` принадлежит агенту, который ведёт карточку: он один раз вписывает абсолютный путь рабочего дерева, в которое входит. Пульт это поле не пишет; его ревью читает ветку там ([локальное ревью](../engineering/local-review.md)).

## Что происходит вокруг записи стадии

Стадию карточки пишут двое: агент, который её ведёт, и оператор — перетаскиванием карточки между колонками или полем `stage` в открытой карточке. Агент правит файл сам, а рука идёт через пульт, и по этому признаку они и различаются: всё, что приходит в записывающий маршрут пульта, — это оператор, а эхо собственной записи агенту не отправляется, потому что её там никогда не было.

После удавшейся записи стадии рукой пульт отправляет в сессию, названную в поле `session`, одну строку на языке страницы: какая стадия была, какая стала, и что писала не она. Это сообщение, а не отказ: обе записи проходят успешно, и без него агент продолжает держать в голове стадию, которую оператор только что отменил, и рано или поздно записывает её обратно. Сессия, до которой не удалось дописаться, не отменяет переезд карточки — пульт отвечает успехом и отдельной строкой говорит, что агент не предупреждён.

Перевод карточки в `done` — это приёмка, и вместе с ней пульт убирает за сессией, ровно в этом порядке: снимает пин, читает последние слова сессии из её транскрипта, дописывает строку в `archive/AGENTS-ARCHIVE.md` с ними и путём к транскрипту, и только потом гасит сессию — мягко, так что её можно поднять снова вместе с историей. Порядок обеспечен кодом: если слова прочитать не удалось или строка в архив не записалась, сессия остаётся работать, а пульт называет шаг, на котором остановился. Гашение до выжимки — единственный способ потерять знание сессии насовсем, и он закрыт. Пульт сообщает и о том, что гасить было нечего: сессия, которой уже нет в списке, названа в отчёте, а не пропущена молча.

Перед приёмкой перетаскиванием пульт переспрашивает, называя сессию. Промах мышью не должен гасить сессию. В открытой карточке того же вопроса нет: чтобы выбрать `done` в списке значений, нужны два осознанных действия, а вопрос на каждое движение карточки сделал бы доску неудобной.

## Как извлекаются заголовок и ссылки

Заголовок карточки и её `[[ссылки]]` на другие заметки читаются из тела, а не из фронтматтера, и у этого извлечения есть два намеренных слепых пятна:

- Перед поиском заголовка или ссылки тело сканируется на предмет блоков кода в ограждении (открытых тремя обратными кавычками или тремя тильдами), и всё внутри ограждения сначала затирается. Строка, похожая на `# заголовок`, или строка, похожая на `[[ссылку]]`, которая встречается только внутри примера в блоке кода, не подхватывается как настоящий заголовок карточки или настоящая ссылка. Это удерживает заголовок и ссылки карточки привязанными к тому, о чём карточка на самом деле, а не к тому, что случайно оказалось в процитированном фрагменте.
- Ограждение, которое открыто, но никогда не закрыто, затирает всё от открывающего маркера до конца файла. Всё после незакрытого ограждения, включая настоящий заголовок или настоящую ссылку, теряется молча. Закрывайте каждое ограждение, которое открываете.

С затёртыми ограждёнными областями заголовком становится первая строка, соответствующая заголовку markdown первого уровня (`# ...`) где-либо в теле — обычно это собственная строка заголовка в шаблоне карточки. Каждая ссылка вида `[[...]]` собирается как ссылка; ссылка с якорем на заголовок (`[[note#heading]]`) или с алиасом (`[[note|alias]]`) записывается по своей голой цели, `note`, с отброшенным якорем или алиасом. Хранимый текст тела карточки всегда — нетронутое исходное содержимое файла: затирание, описанное здесь, — это только рабочая копия, используемая для поиска заголовка и ссылок, и она никогда не записывается обратно и не показывается как тело карточки.

## Документы карточки

Разборы, результаты исследований и дизайн-доки карточки — markdown-файлы под каталогом документации: `docs` внутри доски или `docs` рядом с ней, как раскладывает рабочий каталог fleetdeck. Карточка ссылается на документ так же, как на другую карточку, — по имени: `[[2026-09-13-card-artifacts]]`. Более длинный хвост пути, например `[[reports/2026-09-13-card-artifacts]]`, нужен только тогда, когда у двух документов одинаковое имя файла.

Эти ссылки — единственная запись о том, какие документы относятся к карточке; поля во фронтматтере для них нет. Панель показывает документы карточки вкладками в самой карточке, рядом с сессией, которая написала открытый документ. Документ из раздела документации или из карточки, которая на него не ссылается, открывается в читалке поверх доски. И вкладка, и читалка называют все карточки, которые ссылаются на документ: обратная связь вычисляется из карточек и разойтись с ними не может.

Документ может назвать сессию, которая его написала, в собственном фронтматтере:

```yaml
---
session: e62e1d58
---
```

Значение — короткий id сессии, в том же виде, что `session` карточки. Панель открывает эту сессию рядом с документом, и ответ на вопрос из документа приходит тому, кто его задал. Сессия, которая переписывает чужой документ, ставит свой id: отвечать будут тому, кто документ сейчас ведёт. Поле необязательное; у документа без него автором считается `session` карточки, из которой документ открыт, и панель это подписывает. Остальные поля фронтматтера (`date`, `cards`, `prs`) свободные. Проверяя всю доску, валидатор отвергает `session`, не похожий на короткий id, и незакрытый фронтматтер; проверяя одну карточку, документы не трогает.

Документ, записанный путём — `docs/reports/x.md`, в обратных кавычках или без, — из карточки не открыть, поэтому валидатор такой путь отвергает и называет ссылку, которой его заменить. `scripts/link_docs.py` переписывает пути в карточках, заведённых до этого правила; без `--write` он только печатает, что поменяет.

Путь к файлу в репозитории задачи, ветка, PR и снимок экрана документами доски не считаются и остаются текстом. Имя, общее для двух документов, не открывает ни один из них: панель показывает его неработающей ссылкой, а не выбирает один наугад.

## Что делает карточку нечитаемой

Карточка не разбирается ровно в двух ситуациях: файл вообще не начинается с блока фронтматтера (нет ограждения `---` в самом начале), либо фронтматтер присутствует, но не является валидным YAML. В любом случае карточка не выбрасывается с доски: она сохраняется, помечается как содержащая ошибку разбора и показывается как нечитаемая, а не молча исчезает. Файл, который вообще нельзя прочитать с диска — отказано в доступе, либо файл удалён между листингом каталога и его чтением, — обрабатывается так же: как карточка, несущая ошибку, а не как повод прервать сканирование остальной доски.

Одна сломанная карточка никогда не прячет остальные: остальная доска сканируется и показывается как обычно. Сломанная карточка также исключается, с обеих сторон сравнения, когда пульт проверяет, какие карточки сменили стадию с последнего раза, как он смотрел, — так что наполовину записанная карточка не может вызвать ложное уведомление «переехала в blocked» или «переехала в review».

## Два разных уровня строгости

Код на Go, который пульт использует для чтения карточек (`internal/board`), и Python-валидатор (`plugin/templates/board/scripts/validate_cards.py`) читают один и тот же формат файла, но проверяют не одно и то же. Пройти один — не то же самое, что пройти другой.

| Проверка | Go-читалка (`ParseCard`) | Go-писалка (`SetField`) | Валидатор |
| --- | --- | --- | --- |
| Неизвестное поле фронтматтера | игнорируется | игнорируется | отклоняется |
| `id` | читается и показывается; отсутствие показано как «без номера» | пишется один раз, при заведении карточки, и больше никогда | обязателен; проверяется формат, совпадение с именем файла, отсутствие дублей и захват номера в реестре |
| Наличие обязательных полей | не проверяется | не проверяется | обязательны: `zone`, `stage`, `progress`, `created` |
| `zone` — одно из четырёх допустимых значений | не проверяется | не проверяется | проверяется |
| `created` соответствует `YYYY-MM-DD` | не проверяется | не проверяется | проверяется |
| `session` соответствует шаблону шестнадцатеричных символов | не проверяется | не проверяется | проверяется |
| `stage` — одно из пяти допустимых значений | не проверяется | проверяется | проверяется |
| `progress` — одно из семи допустимых значений | не проверяется | проверяется | проверяется |
| `stage: done` требует `progress: 100`, и наоборот | не проверяется | проверяется | проверяется |
| Начатая стадия требует непустого `session` | не проверяется | проверяется | проверяется |

Карточка, которую начинает пульт (`CreateCard`, за кнопкой **+ карточка**), — единственное, что код на Go пишет целиком, и она пишется так, чтобы проходить валидатор: ровно `zone` — одно из четырёх допустимых значений, с проверкой, — `stage: new`, `progress: 0`, пустой `session` и `created`, плюс заголовок. Тест запускает сам валидатор на такой карточке во всех четырёх зонах.

Go-читалка — это снисходительная читалка и хирургическая писалка трёх полей; она не строилась как страж схемы. Валидатор — это строгий страж, и его нужно запускать намеренно — человеком или агентом, — поскольку ничто в коде на Go его не вызывает. Карточка, которую пульт читает без жалоб, всё равно может не пройти валидатор, а карточка, которая не проходит валидатор, всё равно может быть прочитана пультом и получить обновлённое поле `stage` или `progress` без какого-либо предупреждения о том, что с ней ещё что-то не так.

## Гонка при записи карточки

Запись пульта задумана как хирургическая: он перечитывает файл непосредственно перед записью, меняет только то одно поле, которое его попросили изменить, и оставляет остальное нетронутым, байт в байт. Сама запись атомарна — временный файл записывается рядом с оригиналом, а затем переименовывается поверх него, — так что читатель никогда не увидит наполовину записанную карточку.

Это сужает гонку с агентом, дописывающим строку в лог той же карточки, но не закрывает её полностью. Перечитывание пультом происходит за какое-то время до его переименования, и это окно не равно нулю. Строка лога, которую агент дописывает внутри этого окна, теряется молча, хотя файл никогда не остаётся в сломанном состоянии. Измерено под искусственной нагрузкой: это происходит примерно раз на двести итераций.

Замок, который закрыл бы это окно, не добавлен, и это осознанный выбор, а не недосмотр. Агенты, дописывающие в карточку, делают это обычной правкой файла и вообще не берут файловую блокировку. Замок только со стороны пульта не защищал бы ни от чего — агенты его всё равно не ждали бы, — при этом в коде он выглядел бы как защита, которой на деле нет. Чтобы по-настоящему закрыть эту гонку, нужно менять конвенцию с обеих сторон: либо агенты перестают редактировать карточки напрямую и идут через пульт, либо и пульт, и агенты честно берут один и тот же замок. Любое из этих изменений затрагивает работу всего флота, а не только пульта, и ни одно из них не сделано. Принятая цена — редкая потерянная строка лога в обмен на то, что доска остаётся набором обычных markdown-файлов, которые может редактировать напрямую кто угодно и что угодно.

## Что означает неудачный коммит

После того как пульт записывает поле, он коммитит этот один файл в git с сообщением, описывающим изменение. Если этот коммит не удаётся, поле уже записано в файл — сначала происходит запись, и коммит — отдельный шаг после неё. Ошибка коммита не означает, что правка не вступила в силу; она означает, что правка лежит в рабочем дереве без соответствующего коммита. Повторное применение той же правки в ответ на ошибку коммита было бы избыточным, а не исправляющим действием.

Один из способов, которым коммит может не удаться, — зависание на приглашении ввести парольную фразу для подписи коммита, когда рядом никого нет, чтобы ответить. Пульт не ждёт этого бесконечно: каждая git-операция ограничена по времени, и коммит, который всё ещё не завершился далеко за этой границей, завершается ошибкой, называющей вероятной причиной приглашение подписи, а не зависает.

Пульт, открытый из Dock или перезапущенный обновлением, macOS запускает с `PATH=/usr/bin:/bin:/usr/sbin:/sbin` и больше ничем, и программы подписи, поставленной Homebrew или чем-то подобным, в нём нет. Поэтому git — и `claude` — пульт запускает с `PATH` вашей login-оболочки: при старте он один раз, в фоне и без терминала, выполняет `$SHELL -l -c` и читает напечатанный ею `PATH`. Коммит в первые мгновения после старта дожидается этого ответа. Login-оболочку, которая упала или не ответила за пять секунд, повторно не ждут: пульт оставляет `PATH`, с которым его запустили, добавляет к нему существующие из `/opt/homebrew/bin`, `/opt/homebrew/sbin`, `/usr/local/bin`, `/usr/local/sbin` и `/opt/local/bin` и пишет об этом в журнал. Коммиты подписываются ровно так, как велит ваша настройка git; пульт подпись не отключает никогда.
