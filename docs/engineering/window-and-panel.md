# App, panel and update: field notes

This page is for whoever works next on the fleetdeck app, the panel it starts, or the Update button. It covers what the code relies on and the things that are easy to get wrong. It was written on 2026-09-11, when the app became the panel's owner (#97), the panel came to live exactly as long as the app (#108), and the Update button arrived (#111). The code comments hold the details; this page is the map, with the numbers that were measured and the mistakes that were made.

For the live terminal, the window's web view, and the terminal bridge, see [live-terminal.md](live-terminal.md).

## Who owns the panel

The panel lives exactly as long as the app. That rule was set by the operator on 2026-09-11. Before it, the panel outlived the window by design, and a panel left behind by an earlier window is how a new window came to show an old build.

The panel keeps the rule itself, so no way of the app ending is missed:

- The window starts the panel directly, as its own child, with `--owner-pid` set to the window's PID (`panelArgs` in `cmd/fleetdeck-window/owner.go`). It is never started through a shell. `TestAStartedPanelIsTheStartersOwnChild` fails if a process appears in between.
- At start, the panel checks that `getppid()` is that PID and refuses otherwise (`checkOwner` in `cmd/fleetdeck/owner.go`).
- It then asks the kernel to say when that process exits: kqueue `EVFILT_PROC` with `NOTE_EXIT` on macOS, a pidfd polled for `POLLIN` on Linux. Nothing is polled on a schedule. The exit gets the same graceful shutdown as SIGTERM, bounded by five seconds.
- A watch that cannot be set up counts as the window gone, and `ESRCH` at registration means the owner has already exited. A panel that cannot tell whether its window lives must not risk outliving it.
- The red button only hides the window (`installCloseToHide`). The process runs on, and so does the panel.
- The owner PID is in the panel's build fingerprint (`/api/snapshot`, `build.owner`). A panel started any other way reports none.

A window that finds a panel already answering (`Keeper.replaceable` in `internal/supervisor/keeper.go`):

- **The panel's window is gone:** the panel is stopped, and the window starts its own.
- **Another window is still open:** its panel is used as it is.
- **Started from a terminal, or not a fleetdeck panel:** used as it is, never stopped.
- **From an app bundle, reporting no owner:** replaced too. This rule is temporary and marked so in the code. Such a panel comes from an app older than the owner rule. The rule is to be removed once every fleetdeck panel answering anywhere reports its owner. Left in past that, it would stop a debugging run started by hand from inside a bundle.

Measured on real processes with the real app on 2026-09-11. The panel was gone 44 ms after the window got SIGTERM and 82 ms after SIGKILL. A panel started from a terminal survived the window.

## A panel of another build

"Used as it is" was also, until 2026-09-14, "used in silence". That day the operator installed v0.9.0 and the window opened on a panel built from source on 2026-09-11 (`de3aa16`), which a launch agent left by an earlier `init` kept on 7777. The header is drawn by the panel's page from the panel's build, so it showed that commit and the old page's always-present Update button, and nothing said the panel was not the app's build. The operator went looking for a defect in a release that had none. The window now says so (`cmd/fleetdeck-window/foreign.go`). What it relies on:

- **Decided: the commit decides.** The keeper reports what a panel it did not start says of its build (`Event.Holder`), and the window compares `vcs.revision` and `vcs.modified` with its own. A release and a build from a checkout of the same commit are the same code, whatever version each carries. A window with no commit of its own compares release versions only, and otherwise says nothing.
- **Decided: the window draws the notice, not the page.** The page is the other build's and may be of any age; the operator's was from before any of this. The window adds a user script with webview's `Init`, which runs in every page it loads, and the script asks the window over a binding what to show. **Read in `internal/server/static.go`:** the panel's Content-Security-Policy has `script-src 'self'`, so an inline `onclick` in the notice would be refused; the script adds the button's listener itself. `style-src` allows `'unsafe-inline'`, which the notice's inline styles need. The header's build is marked as the panel's with a `#header .build-rev::before` rule, from outside the page, because that markup is the one every header has had since the build was shown there.
- **Decided: the launch agent is recognised by its file, not by `launchctl`.** `~/Library/LaunchAgents/dev.fleetdeck.panel.plist` with that `Label`, read with `/usr/bin/plutil` by absolute path. It keeps the panel when its program is the panel's binary. The window never removes it: removing it is the person's, as loading it was, and the notice shows the two commands `init` prints. An agent loaded and then deleted from disk is not named; a file never loaded is named as though it were. Both were accepted: the file is what `init` wrote and what survives a reinstall. **Known, not fixed:** the agent keeps the panel only when its program and the panel's binary are the same file. An agent that starts the panel through a wrapper script is named without that, the notice offers the button, and a replacement would fight `KeepAlive`.
- **Decided: replacing is offered only where it can hold.** There is no button for a panel the agent keeps, since `KeepAlive` would start it again at once and the two would fight for the port, and none for the panel of another window still open.
- **Decided, after review: a press names the panel it was shown, and the port is looked at again before anything is stopped.** The first version stopped whatever fleetdeck panel held the port when the button was pressed. The port can change hands without going quiet: a second window's panel started within the two looks it takes to see a panel gone. And the press need not be a person's, because the window's bindings are callable from the page, and the page is the panel's. So the keeper reports the PID on the port with the build (`PanelBuild.PID`, from `lsof`), the button hands that PID back, and the window takes a press only for the notice it shows now. At the press the keeper reads the build and the PID again. It stops nothing unless they are exactly what was shown, the panel reports no window, and the window's `MayReplace` still agrees. It then signals that PID only while `lsof` still names it (`stopListener`). A press that does not hold stops nothing and reports whoever is on the port. The keeper also reads the build at every look while it uses such a panel, and reports it again after two looks in a row show another build, so the notice does not go on describing a panel that has left.
- **Measured on a stand, 2026-09-14** (`TestAStandWindowNamesAPanelOfAnotherBuildAndIsQuietOverItsOwn`). A `dist-app` build (ad hoc, arm64, `v0.9.1-t055`) was started over two panels in turn: `de3aa16` and `v0.9.0`, each run from a terminal with a HOME and port of its own, the agent's plist a file in that HOME and never loaded. Over the agent's panel, the window's log named both builds, the binary and the agent. The page reported painting the notice, with the commands and without a button, 3 s after the first window started and at once after that. The panel killed, the window started its own and took the notice down within 4 s, which is two missed looks at the 2 s poll. Over a panel from a terminal, the notice carried the button. Over a panel of the app's own build, copied out of the bundle and run from a terminal, nothing was shown for 5 s after it answered.
- **Not verified:** an agent actually loaded into launchd, which was not done on this machine; the button pressed in a real window, since a click into a WKWebView cannot be made from a test (`Keeper.Replace` is covered by the supervisor tests); the header mark seen by a person.

## The PID reuse trap

A PID is a number the kernel hands out again once the process that had it is gone. Anything that reads a PID now and acts on it later can act on a different process. How each place here deals with that:

- **The panel and its window.** The panel does not trust the number it was given; it checks that the number is its parent. A process's parent PID cannot belong to a stranger: when the parent dies, the child is handed to launchd and `getppid()` becomes 1. So a panel whose owner has already died refuses to start instead of watching whatever took the number.

  Between the check and the kernel watch there is a gap, and the window can end inside it. Either way the answer is the same:

  - **The window ended before the watch was set up.** On macOS, registering `EVFILT_PROC` for it fails with `ESRCH`. On Linux, `pidfd_open` fails with `ESRCH` once the process is reaped. If it is not yet reaped, the pidfd opens and is readable at once. The panel reads all of these as "the owner is gone" and shuts down.
  - **The window ended after the watch was set up.** The watch fires.

  Only one case is left. The window dies inside the gap, and its PID is handed to a new process before the registration, which then watches that stranger. On Linux the pidfd rules even this out, because it is bound to the process it was opened for, not to the number. On macOS it would take the PID being reused within microseconds. That is not guarded against and not expected. A second `getppid()` check after registering would close it.
- **Stopping a panel.** `StopHolder` asks the kernel who listens on the port (`lsof -nP -t -iTCP:<port> -sTCP:LISTEN`) at that moment, and only after the holder answered as a fleetdeck panel. It never uses a PID remembered from earlier, and never matches a process by name. Matching by name is how the old rebuild script stopped panels, and it would stop the wrong one the day two installs coexist.
- **Whether a panel's window lives.** The keeper uses `kill -0` on the owner the panel reports. If that PID has been handed to some other process, a panel whose window is gone looks like one with a live window, and it is used for the moments until its own watch shuts it down. The mistake costs seconds, not a wrong stop.
- **Test stand-ins.** They watch their test process with `kill -0` every 100 ms. In tests only, the worst case is a stand-in that lives longer.

## launchd, its throttle, and the keeper

Until 2026-09-11 the panel was started at login by a launch agent that `fleetdeck init` wrote, and launchd kept it alive (`KeepAlive`). The app replaced that agent. A leftover agent would start a second panel at every login, so `init` now names one it finds and prints the two commands that remove it: `launchctl bootout gui/$(id -u)/dev.fleetdeck.panel`, then removing the plist. `init` never runs them. `bootout` is the current spelling; `unload` is listed as legacy in `man launchctl`.

That agent had `KeepAlive` set to plain `<true/>`: start the panel again whenever it exits, for whatever reason. On a taken port the panel names the holder and exits with status 1 (`log.Fatalf`). launchd then starts it again once `ThrottleInterval` has passed, it fails again the same way, and so on: every ten seconds, for as long as the port is taken, with another "cannot take its port" in the log each time. Nobody is told.

`KeepAlive` as a dictionary with `SuccessfulExit` does not cure that. Read from `man launchd.plist`, not measured here:

- **`SuccessfulExit` false** restarts the job only when it exits non-zero. A taken port is a non-zero exit, so the loop stays.
- **`SuccessfulExit` true** restarts it only when it exits with zero. The taken-port loop stops, but so does the restart after every real crash, which is what `KeepAlive` was for.
- **A panel that exits with zero on a taken port**, to break the loop under `false`, would make a panel that could not start look like one that stopped on purpose.

An exit status cannot say "the port is taken, and a person should look". So the keeper does not guess from exit codes. It judges by how long the panel stayed up.

The keeper does what launchd did, including launchd's throttle. launchd will not start a job again sooner than `ThrottleInterval` after its last start, 10 seconds by default. The keeper's `MinUptime` is the same 10 s (`launchdThrottle` in `cmd/fleetdeck-window/owner.go`). A panel that dies within it is not restarted: a panel that dies at once dies at once again. The window says so, shows the end of the panel's log, and offers a button to start it again.

How long a started panel has to answer: `panelStartTimeout` = 110 ms × 3. The 110 ms is the worst of ten measured starts. They were ten separately built binaries, each run for the first time, polled the way the keeper polls. A start straight after login, with a cold disk cache, was not measured.

## Why a taken 7777 is reported, not worked around

The panel answers on `127.0.0.1:7777`. Three things point at that port without asking anyone:

- the window (`defaultURL` in `cmd/fleetdeck-window/main.go`);
- the statusline reporter, `fleetdeck-status`, which posts every session's status to `http://127.0.0.1:7777/api/status` unless `FLEETDECK_ENDPOINT` is set;
- whatever the operator has open in a browser.

Where the window's panel listens is the window's to say, since v0.11.0: the window starts every panel with `--port`, the port of the URL it looks at (`panelArgs`, `panelPort` in `cmd/fleetdeck-window`), and the app, opened with no `-url`, passes `--port 7777`. Until then the window passed no port, and its panel listened on `server.port` from the config, whatever URL the window looked at. `server.port` is now only where a panel started without `--port` listens — one started from a terminal. A dev app on another URL relies on this (`dev-app.md`).

A panel that moved to another port would be invisible to all three. The statusline reports would go nowhere, and the context and state they carry would silently vanish from the panel. The old panel would keep running unseen. So a panel that cannot take its port does not look for another one. It names what holds the port and exits (`portHolder` in `cmd/fleetdeck/portholder.go`), asking the holder for one second at most. There are three answers: another fleetdeck panel, by commit and binary path; something that is not fleetdeck; or something that took the connection and did not answer.

## Handing the panel to a new version

The Update button (`internal/supervisor/update.go`, `cmd/fleetdeck-window/update.go`) puts the new app beside the installed one, and lets the new version put itself in place. The invariant, in the operator's words and in the code: at the canonical path there is always a working version, at any moment.

Where the new app comes from is the one thing that differs between builds, and it is behind `supervisor.Source`: a build from a checkout brings that checkout forward and builds it (`TreeSource`), and one installed from a release downloads the next release and checks who signed it (`ReleaseSource`, and [update-from-release.md](update-from-release.md)). Steps 2 and 3 below are that source's half; everything else is the same code for both, which is the reason for the seam.

1. The old window takes the update lock. It is an flock beside whatever the build updates from — the source tree for a build that has one, the installed app otherwise — so a crashed update never locks the next one out.
2. It asks the source what there is to update to, and stops here when that is what already runs. A tree is fetched and reported on without being moved; a releases page is asked which release is newest. A tree on another branch, with edits, or with commits of its own is refused in words.
3. It has the source put the new app into `.fleetdeck-update/` beside the installed bundle: built there from the tree, or downloaded there and checked — signed with a Developer ID, by the same Apple team as the running app, and notarized — before anything else happens. A download that fails any check is deleted and the update stops.
4. It pauses its own keeper. A keeper left running would race the new window for the port; a test holds this.
5. It starts the new window from the build with `--handover <file> --canonical <installed bundle>`, and from v0.10.1 on with `--handover-timeout <its deadline>`.
6. The new window reports `alive`, stops the old panel, and starts its own from the staged bundle — the only place the new build exists at this moment, since nothing has touched the canonical path yet. Its keeper starts only after the old panel is stopped, so the replacement rules above never come into play here.
7. It checks that the new panel answers with the build the window is, then reports `panel`.
8. It exchanges the staged and installed bundles in one system call: `renamex_np` with `RENAME_SWAP` on macOS, `renameat2` with `RENAME_EXCHANGE` on Linux. Then it has LaunchServices forget the staged path and take the canonical one, and only then reports `swapped` (see "Where the next launch goes").
9. It restarts its panel, this time from the canonical path, and reports `done` once that panel has answered. The old window quits; the new one opens the panel's page only now (see "The new window's page").
10. Once the old window has quit and its update has let go of the lock, the new window removes the bundle swapped out. The handover file and `new-window.log` stay.

A handover that fails ends with the old window resuming its panel and the new window quitting; the old window's error names the new window's log, `.fleetdeck-update/new-window.log`, so the person is not left to press again without knowing why.

### Where the next launch goes

On 2026-09-14 an update from v0.9.0 to v0.9.1 went through, and the next time the operator opened the app it was v0.9.0, running from `/Applications/.fleetdeck-update/fleetdeck.app`. The new window had started from the staged path, and a window started by exec from a bundle puts that bundle's path into LaunchServices (measured below, and again in the section on taking the panel over before the window is made): from then on the database held two bundles under `dev.fleetdeck.window`. After the swap, the staged path held the old version.

Measured the same day with a probe bundle of its own identifier (`dev.fleetdeck.t057probe`), replaying the incident: the installed bundle opened once through LaunchServices, a newer one started from `.fleetdeck-update/` by exec, the two swapped while it ran, then it quit.

- `NSWorkspace.urlForApplication(withBundleIdentifier:)`, `open -b` and `open -a` all opened the staged path, which held the older version. Neither the newer version nor the installed path won.
- A Dock-style bookmark of the installed bundle resolved by path, to the installed bundle (`stale=true`). So the Dock was not the cause.
- `open <installed path>` opened the installed bundle.
- `lsregister -u <staged>` right after the swap, or removing the staged bundle, made all three open the installed bundle. `-u` took 10–13 ms and `-f` 20–25 ms, well inside the handover's budget.

Not measured: whether macOS checks a window running from the staged path in again when it is later activated. That is why the staged bundle does not survive the update (step 10): nothing goes back to it, and left in place, it is the old version under the app's own identifier. It is removed only after the old window's update has let go of the lock, because until then the old window is running out of it.

**Why LaunchServices moves before `swapped`, not after.** A handover can still fail once the swap is done: the old window gives up when `done` does not come within its own deadline (see "Stopping the staged panel"). Checked on a stand on 2026-09-14 (T-060) with a new window that stalled right after reporting `swapped`, when LaunchServices was still told only afterwards. The old window failed with "the new window reported "swapped" and then nothing". The canonical bundle held the new build, `.fleetdeck-update/fleetdeck.app` the old one, and the only path LaunchServices knew for the stand's identifier was that staged path. That is the incident above, back again. Nothing cleans it up: the staging directory stays until the next update, and that update's `os.RemoveAll` removes the directory without having LaunchServices forget it. The new window now has LaunchServices forget the staged path and take the canonical one right after the swap and before it reports `swapped`, so the old window can never read `swapped` while the staged path is still registered. Failing to tell LaunchServices is logged, not fatal, as before. Measured the same day on this machine, 10 rounds: forgetting the staged path took 5–7 ms and registering the canonical one 14–23 ms, together 19–30 ms. The handover already paid for both in every stand run below; moving them earlier costs nothing extra.

A window that finds itself in `.fleetdeck-update/` without `--handover` is not the installed app. That is the other half of the incident: the v0.9.0 window LaunchServices opened took its own bundle for the installed one, updated itself inside the staging directory, and left `.fleetdeck-update/.fleetdeck-update/`. Such a window now has LaunchServices forget its bundle, opens the installed app above every staging directory by path, and quits before it has a window or a panel (`cmd/fleetdeck-window/staged.go`). It leaves the staging directory itself alone, since another update may be running there. With no installed app beside it, it shows a page saying so, with both paths, and starts no panel. Its update refuses with `staged` in any case.

### The new window's page

The same update left the new window white, and on the next try on "Принимаю пульт" counting seconds, with `done` in the handover file both times. The window took the panel's first answer as its page being shown: it navigated, set `showingPanel`, and let every later answer go by. The handover restarts the panel from the canonical path a moment after that first answer, while the page was still loading. When the document had come and its styles and scripts had not, the result was a white window: `web/index.html` has no background and no content of its own without `app.css` and `main.js`. When the navigation was refused before anything arrived, WKWebView kept the page before it. `webview_go` sets no navigation delegate, so nothing said either.

Now:

- The new window does not ask for the panel's page until `done`; the handover page stays up through both starts.
- A script injected into every page (`pageLoadScript`) says, on the panel's origin only, whether the page loaded with `app.css` applied and `main.js` run (`main.js` sets `data-fleetdeck-page`), and when it goes away.
- The window sets its own navigation delegate (`nav_darwin.c`) and logs what WebKit says of each navigation: started, committed, finished, failed with its error, and the web content process it ran in. It logs each page of its own it puts up, by its heading. Setting a delegate changes one thing WebKit does by itself: a page whose web content process went away is left blank rather than reloaded (`NavigationState::NavigationClient::processDidTerminate` reports the termination handled), so the window asks for the panel's page again itself, whether it was showing or still asked for. Under a shown panel it does so once, as WebKit would (`maximumWebProcessRelaunchAttempts`, with the count cleared 30 s after a finished load): a second loss within 30 s of the last finished load puts up a page saying the panel's page keeps going down, with a button to open it again, rather than reloading a page that takes its process down every time.
- Until the page has said so, the window asks for it again when a panel answers again, when WebKit says the navigation failed or its web content process went away — after `navFailedRetryPause`, so that three tries are not spent within milliseconds — and when time goes by: `navSilentWait` from the ask for a navigation WebKit has not committed, `pageLoadingWait` from the moment its document began (WebKit says it committed, or the script says `loading` as the document starts). A navigation that failed because another took its place (`NSURLErrorCancelled`, or WebKit's frame load interrupted) is not the page failing. The page's word is taken only once WebKit has committed a navigation since the window last asked: the word comes through the UI thread's queue, and a late one from the document the ask cut off is not about the new one. What a page says after the window has covered it with a page of its own is not taken either. A window whose delegate never reports takes the page's word as before there was a delegate, and puts the failure page up only after `pageLoadTries` times `navSilentWait`, about 15 s. Asking again cuts a load off and starts it over, so a navigation is not asked for again while the window's web content process may still be starting. The window asks for the address the page last said it was at, not its own URL: its own URL is the start page, and a page that left for a fleet (`?fleet=`) would lose it. A page that left and has not yet said where the next one began is not asked for at all — the window does not know where it went — and is only reported if nothing begins within `pageLoadingWait`. After `pageLoadTries` in a row the window shows a page saying the panel's page did not load, with a button to try again. That page and its button were not checked by hand on the operator's machine: screenshots from the macos-15 runner show the page drawn, and unit tests cover the binding the button calls.
- Every page the panel serves sets the mark: `index.html` through `main.js`, `start.html` through `start.js`, `setup.html` through `setup.js`. The window opens `/`, which a configured panel answers with the start page. The first version of the check knew only `main.js` and `/app.css`, and on a stand it took the start page for broken ten times in ten; a test now walks every page in `web.FS`.

Until 2026-09-14 the wait for a navigation that had not reached its document was `pageLoadWait`, 531 ms: the worst of twenty page loads timed on a stand, 177 ms, three times over. It was too short for a window just started, whose first navigation waits for its web content process to start. On the operator's update that day the web content process answered the policy check of the first ask 1.38 s after it, by which time the window had asked three times, and only the third ask's page came. On GitHub's macos-15 runner, in the window-on-oldest-macos job, two runs of three put the failure page up over a panel that answered. Twenty runs there with WebKit's navigation events logged showed WebKit commit the first navigation 0.20–1.69 s after the first ask, and the run at 1.69 s put the failure page up; the system log of another showed the web content process busy the whole time from its launch to its first policy answer, with no pause over 0.21 s — starting, not hung. `measuredWebContentStart` is the worst of these, 1.69 s, and `navSilentWait` is three times that. On a stand on the operator's machine a window's first navigation started 1.57 s after it was asked for. Six update stands there the same morning started it 3–5 ms after the ask; why the start is slow on some machines and starts and not on others was not found.

`pageLoadingWait` is the wait for a document WebKit has committed, counted from the commit. It was 840 ms — three times 280 ms, one load on the update stand timed from the ask, before the window could tell the ask from the commit — and on GitHub's macos-15 runner that was too short. In PR #166's window-on-oldest-macos run of 2026-09-14 the board's first document committed, WebKit said it finished 719 ms later, and the page said it was the panel 952 ms after the commit; the wait ran out at 840 ms, the window asked again, and the document that was loading was cut off. Timed from the commit to the page saying `panel` in every window log the runner kept that day — PR #166, T-058's three runs of window-on-oldest-macos and T-059's two diagnostic runs, 28 documents no ask cut off — the loads took 34–740 ms, and the one that was cut off 952 ms. The worst, 952 ms, three times over is 2856 ms. A committed document that fails, or whose web content process goes away, is not waited on: WebKit says so and the window asks again at once. The wait is only for a document that goes quiet.

### The panel is started twice, and both starts are load-bearing

Steps 6 and 9 are two starts of two panel processes by one window, from two different directories, and an update therefore shows up in `~/Library/Logs/fleetdeck.log` as two `shutting down` / `listening` pairs about a second apart. Both name the new version and the same URL, and until T-041 neither said which bundle it was started from, so one update read as two crashes. It was read that way by the operator on 2026-09-12 (T-033), which is why this section exists. The `listening` line now ends with the path of the binary serving (`servingLine` in `cmd/fleetdeck/main.go`), and the two starts of one update name two different bundles:

```text
fleetdeck v0.6.0 listening on http://127.0.0.1:7777 from /Applications/.fleetdeck-update/fleetdeck.app/Contents/MacOS/fleetdeck
fleetdeck v0.6.0 listening on http://127.0.0.1:7777 from /Applications/fleetdeck.app/Contents/MacOS/fleetdeck
```

Neither start can go. The first one cannot be from the canonical path: the old version is still there, and it stays there until the new build has shown it works, which is the invariant. The second one is needed for three separate reasons, any one of which would be enough:

- **The staged path holds the old version once the swap has happened.** The keeper starts a panel by path, not by inode, so a panel left running from `.fleetdeck-update/` leaves the keeper's `Bin` pointing at the bundle that was swapped out. The first time that panel died, the keeper would start the *previous* version — a silent downgrade at an arbitrary moment. Measured on 2026-09-12: after an update from v0.5.0, `.fleetdeck-update/fleetdeck.app` answers `v0.5.0`.
- **Nothing would ever have run the installed app from the path it is installed at.** The restart is the one execution of the canonical bundle from its final path before `done` is reported, while the old window is still alive to be told that it failed. This is the same standard the release path's acceptance holds itself to: the app at the canonical path is asked what it is by running its panel, not by reading metadata around it.
- **The panel writes its own path outward.** `os.Executable()` is the path it was started from. It reaches `/api/snapshot` as `executable` — which is how "which panel answers on the port" is decided — and it reaches `~/.claude/settings.json`: `ensureStatusline` in `cmd/fleetdeck/init.go` writes the `fleetdeck-status` beside the running panel into `statusLine.command`. A panel left running from `.fleetdeck-update/` would write a path inside the directory the *next* update removes with `os.RemoveAll`.

Setting `Keeper.Bin` without restarting would answer the first reason and neither of the other two.

Swapping first and starting the panel once would be one start instead of two, and is refused for the invariant: the exchange would then happen before anything had shown the new build works, and a broken build would be sitting at the canonical path.

The handover was designed while the panel still outlived its window, and it came through the change to "the panel lives exactly as long as the app" (#108) with no step changed:

- **The new window never adopts the old panel.** It stops it, always, and starts its own. The old window's panel was going to go anyway, when the old window quits after `done`.
- **The new window's keeper starts only after the old panel is stopped.** So the keeper never meets a panel it would have to judge, and none of the replacement rules come into play.
- **The new window's panels are its own children,** started with its PID as their owner, like any window's.
- **A new window that fails and quits** takes its panel with it by the owner rule, on top of stopping it explicitly.

Before the swap, a failure stops the staged panel and reports `failed`. The old window then starts its panel again, from the installed bundle as it was.

The handover file carries one line per step. A line not yet ended by a newline is not read, so a half-written step is never taken for a whole one.

The swap is watched in a test (`internal/supervisor/swap_test.go`). A reader stats the canonical path in a loop while bundles are exchanged. In one Linux run it found the path missing in 0 of 1274 reads. The control is the same reader during two-step replacements, where it found the gap in 2137 of 4918 reads.

The handover timeout was measured on 2026-09-11 on the operator's machine, with the fleet running. It covered ten real handovers, each a new window from a freshly built bundle of its own, timed from the new window's start to `done`. In ms: 812, 762, 542, 495, 490, 489, 490, 485, 484, 483. The worst is 812 ms, and three times that, 2436 ms, is `handoverTimeout`. The first two were slower because each binary ran for the first time. A handover straight after login, with nothing of the binaries in the disk cache, was not measured.

The ten were measured before #108. The new window runs the same steps, plus the panel checking its parent and registering one kernel watch at start. Neither should move the number, but it was not taken again.

### Stopping the staged panel

The old window's deadline is its own. `handoverTimeout` is written into the version already installed, and the version replacing it cannot change it: an update from v0.9.2 runs on v0.9.2's 2436 ms however long the new version would like. Everything from the handover to `done` has to fit in it, including stopping the panel the new window started from the staging directory a moment earlier.

Both of the new window's panel starts are held inside that deadline (v0.10.1, `internal/supervisor/takeoverdeadline.go`). The keeper's own ceiling for a start is 3 s, longer than a v0.10.0 window's whole handover, so while a takeover runs each start gets what is left instead. The first start gets what is left less room to swap, stop the staged panel, start the panel again and report; a first start too slow for that fails before the swap. The swap itself is not made without that room. The second start gets what is left less room to fail and report, so `failed` reaches the old window before it gives up and kills a window that has already swapped the bundle. Failing a start takes time as well: the panel that did not answer is stopped before the failure is reported. During a takeover that panel is killed once `handoverStopGrace` is over, and the stop is inside the room kept. CI found this on 2026-09-14: a race-built stand-in took a second to exit on SIGTERM, and the failure reached the old window after its deadline. The deadline is the old window's, not the new window's `handoverTimeout`: a window of v0.10.1 or later passes its own with `--handover-timeout`, and a window started without it keeps to v0.10.0's 2436 ms. It is counted from the new window's process start as the kernel records it, which comes before the old window starts its clock.

The new window takes the panel over before any of its window is made (v0.10.1, `cmd/fleetdeck-window/handoverstart.go`). Until then the takeover began only after the web view, the glass frame, the bindings and codesign. On a cold first start on macOS 26 (run 34861301605, 2026-09-14) the web view was made 1575 ms after the process started. The glass frame was still not made at 2456 ms, when the v0.10.0 window gave up; nothing of that time went before `main`. That runner drew the frame opaque, not in glass (see "the runner had been drawing the frame opaque" below), so how long a cold first start takes to make the glass frame is not measured. Now the takeover runs in its own goroutine from `main`'s first moments, while `webview.New` and the rest of AppKit stay on the main thread. Everything up to `done` goes without the window. What the handover comes to for the window waits until the window is made: the panel's page is asked for at `done`, and the window is closed at a failure. A failure before the window is made ends the process with no window shown, and the old window says why. codesign, which works out how the build updates, runs beside the start too. The window's timed start lines (`startupsteps.go`) say where a start spends its time.

With the takeover ahead of the window, the new window's own registration puts the staged path back after the takeover has had LaunchServices forget it. This is measured. In the end-to-end update from v0.10.0 (T-064, run 34866422965, 2026-09-14) the reregistering described next was taken out, as the check's mutant M3. While the staged bundle was still on disk, `lsregister -dump` showed two records eight times over a minute: `/Applications/fleetdeck.app` and `/Applications/.fleetdeck-update/fleetdeck.app`. The staged record left the dump only once the bundle was removed. With the reregistering in place (run 34863454014) the dump after the bundle was removed held one record. This agrees with the probe of T-057 above: a bundle started by exec from the staged path is what LaunchServices then opens, and forgetting that path or removing the bundle cures it.

So once the window runs, a takeover that has swapped the bundles has LaunchServices forget the staged path and register the installed one again, and mutant M3 in the end-to-end update from v0.10.0 holds that. The window's tests hold it too: `TestAWindowStartedByAnUpdateTakesThePanelOverBeforeItsWindowIsMade` fails with the reregistering taken out (checked on 2026-09-14). The end-to-end check catches M3 only while its dump taken before the swapped-out bundle is removed counts as a failure. If that dump is kept only as information, that test is the one thing left holding the reregistering. Not measured: when in a process's start the registration is made, whether with the application object, when launching finishes, or later. By the time the window runs it has been made, and the reregistering after that point covers either case. A swap made after the window runs is followed by the takeover's own reregistering.

Reregistering does not hold while the swapped-out bundle is on disk, and a person does not look at the dump but opens the app. Both are measured in the same end-to-end update, with no mutants. In run 34867562033, after "telling it again" at 16:20:06.538, the staged path, holding the removed v0.10.0 under `dev.fleetdeck.window`, was registered again at 16:20:07, within about a second; the dump's times are whole seconds. The bundle was still there, and retire came only at 16:20:15.763. On the runner the installed build has the stand's identifier, `dev.fleetdeck.stand`, and only the removed v0.10.0 has `dev.fleetdeck.window`. In run 34869975049 resolving `dev.fleetdeck.window` (`URLForApplicationWithBundleIdentifier`, what `open -b` uses) gave `/Applications/.fleetdeck-update/fleetdeck.app` in the looks that started 10 and 18 s after `done`, while the bundle was still on disk. After retire it gave "": on the runner that means no app under that identifier, not a gap in resolution. `dev.fleetdeck.stand` gave `/Applications/fleetdeck.app` in all 10 looks after retire, and the dump held one record, the installed bundle. On the operator's machine both builds have `dev.fleetdeck.window`, which is the case the probe of T-057 measured: while the staged bundle is there, its path is what opens. A record for the removed path may still be listed for a while: in run 34867562033 the staged record stayed 60 s with "Bundle node not found on disk", and in run 34865270413 there was none.

So removing the bundle is what holds, and removal does not give up (`Takeover.retire`, v0.10.1). Past a minute of close watching, the new window tries again every ten minutes for as long as it runs. It tells LaunchServices again at each try and once the bundle is gone, and it logs why each try left the bundle: the old window still running, the update lock held, or the removal failing. Removal still waits for the old window to quit and for the lock. A window that quits first leaves the bundle to the next start of the installed app (`supervisor.RetireLeftover`), which removes it once, unless an update holds the lock or a process still runs out of it. Only the bundle goes; the handover file and `new-window.log` stay.

On 2026-09-14 (T-060) one update stand run in three missed it after `swapped`: the new window asked its keeper to restart the panel from the canonical path, and `done` never came before the old window killed it. A panel told to stop waits for the collect cycle it is in before it closes its server, and that cycle asked the keychain for the usage token through `security`, which nothing could cut short. Measured on a stand with a HOME at the operator's scale (a clone of the board, transcripts of the sizes the operator's are, 42 live sessions from a stand-in daemon) and a `security` that took 1 s: a SIGTERM 50 ms after the panel started waited 1022 ms, one at 150 ms waited 935 ms. With `security` answering at once the same panel went 2–5 ms after SIGTERM. The transcripts are read from their tail and cost nothing like that.

Now:

- **A panel told to stop does not wait on anything outside it.** The collect cycle runs under the context SIGTERM cancels, and so do the two programs it can start: `security` for the usage token and `osascript` for a banner. The cycle's other sources are files and the daemon socket, all already bounded by that context or their own deadlines; git is run only for a request, never by the cycle or the board watcher.
- **A panel told to stop does not wait on a connection that has asked for nothing.** The failed stand run itself was this, measured with the keeper's and the takeover's steps timed: the staged panel's collect cycle and board watcher stopped at once, and its server took 2113 ms to close, waiting on one connection accepted just before the stop that never sent a request. It closed when the old window's deadline killed the new window: the new window's own probes had opened it. An HTTP server counts such a connection as work for up to five seconds. The panel now closes connections that have asked for nothing when it stops, and any accepted after (`cmd/fleetdeck/conns.go`); a request the server has already read is still answered, for up to `shutdownTimeout`. "Asked for nothing" is as the server sees it: a connection stays new until the server has read a whole request from it, so one whose request has arrived but not been read yet is closed too, and its client sees the connection closed, as with any panel going away.
- **A restart does not wait out the ordinary stop grace.** `Keeper.Restart` is only ever an update's. It gives the panel it replaces `handoverStopGrace`, 300 ms, to go on SIGTERM, then kills it. An ordinary stop still gives `stopGrace`, 6 s.

Measured after these changes, on an update stand with an old window at c0ea864 and a fresh HOME every run (2026-09-14, 20 runs in a row): every handover reached `done` within the deadline, handover to `done` 509–764 ms in 19 runs and 1144 ms in one. That one ran while other sessions loaded the machine (load average 4.6), and most of its extra time went on starting the new window, before either panel was touched. 1144 ms is the worst case, 1.29 s inside 2436 ms. At its stop the staged panel had no connections in any run. The installed panel, stopped first, held one or two connections in most runs, from the old window's own pooled probes; it closes its listener at once, and the takeover waits only for the port, so they cost the handover nothing.

SIGKILL is safe for that panel, and the reason is an inventory, not an assumption. What the panel writes to disk:

- **Without a request, nothing.** The collect cycle and the board watcher only read: the board's cards, Claude Code's job store and transcripts, the keychain through `security`. They may start `osascript` for a banner, which writes nothing of the panel's. The shutdown path writes nothing. `~/Library/Logs/fleetdeck.log` is opened by the window, and the panel only appends to the descriptor it inherits. The rate-limit file is written by `fleetdeck-status`, not by the panel.
- **For a request, only whole writes.** A card's field (`internal/board/write.go`), every write to `config.yaml` (`internal/config/write.go`) and the orchestrator brief (`internal/orchestrator/brief.go`) go to a temp file, synced and renamed into place. A commit to the board is git's own.
- **The two that were not whole are whole now.** Creating a card wrote the new file in place. It is written beside the card now, under a hidden name no scan takes for a card, and linked into place, and a link fails on a taken name exactly as the exclusive create did. `~/.claude/settings.json`, written when the panel is set up and when a fleet is added, was written over in place. It is written beside the file and renamed over it now, through a symlink to where the link points, keeping the file's permissions.
- **What a kill leaves behind is cleared by the next write.** A panel killed mid-write leaves the temp file: `.T-NNN-….md.tmp-*` in the board's `cards/`, `.settings.json.tmp-*` beside the settings. Neither is taken for a card or for settings. The next card, or the next save of the settings, removes such files once they are a minute old; a younger one may be a write in progress. Clearing is done at the next write, not by `.gitignore` alone: the settings are in no repository, and a board already set up never receives a change to the template. The template's `.gitignore` also lists `.*.tmp-*`, so that on a new board a leftover stays out of a commit until then.

Nothing asks the staged panel for anything during a handover on purpose — the new window's page is not opened until `done` — but a browser tab or the old window's page can reach the port in that half second, so whole writes are what make SIGKILL safe, not the absence of requests. The panel's writes to `settings.json` still read the file, change it and write it back while Claude Code may be writing the same file; that race is older than this and is not closed here.

## Test stands on a machine with a live fleet

Everything above is tested on the operator's own machine, next to the fleet he works with. Four things matter there:

- **A panel finds the fleet daemon by uid, not by HOME.** A separate HOME and config do not keep a test panel off the real daemon. `-stand-socket <path>` does (#107): given a path nothing listens on, the panel never discovers the real daemon. Before #107, stand panels listed the real fleet's sessions. Opening one of them on a stand would have resized that session's real terminal for everyone attached.
- **A window on a stand hands the stand's socket to its panels only when told to.** Set `FLEETDECK_STAND_SOCKET` in the stand's environment: the window then starts every panel it starts with `--stand-socket` — the restart after an update's swap included — and an update's new window inherits the variable. Set but empty, the window refuses to start. Without it, the window starts its panels with `--owner-pid` only, and they find the real daemon by uid.
- **The incident that made it so.** On 2026-09-14 a page-load measurement ran a terminal panel with `-stand-socket` from the binary inside a stand's `.app`. The window replaced it — until then a panel running from a bundle and reporting no owner was taken for one left by a window from before #108 — and started its own without `-stand-socket`, ten times, each for under a second. The page never ran its scripts, and the operator's panel and all six sessions were checked afterwards and found untouched. What was at risk, as a fact: the daemon accepts an attach with no control key, for reading — the attacher receives the session's terminal output — and the attach, and any later resize, which asks for no key either, resizes the session's terminal (`internal/daemon/attach.go`). Only typing is refused. That replacement rule is gone: a panel the window did not start is used as it is.
- **A stand uses its own port** (7790 here), with its own HOME, config and board. It is never 7777.
- **A stand is built under its own bundle identifier**, `dev.fleetdeck.stand` (`make window-app BUNDLE_ID=dev.fleetdeck.stand`, and the same for `dist-app`). macOS keeps every bundle it is shown under its identifier, long after the directory is gone, and opening "fleetdeck" may open any of them. On 2026-09-14 the operator's machine held some sixty `fleetdeck.app` registrations from stands, test runs and mounted images, almost all under `dev.fleetdeck.window`. Tests build under the stand identifier and hand every bundle they build, copy, mount or start to `forgetBundle`, which has LaunchServices forget it when the test ends. A downloaded release keeps the app's identifier and is only safe once forgotten. Check before and after a stand by identifier, not by name — a bundle under the app's identifier may be called anything, and on 2026-09-14 some were (`sigprobe/tampered.app`, `mutant.app`): `NSWorkspace.urlsForApplications(withBundleIdentifier:)` for `dev.fleetdeck.window` and `dev.fleetdeck.stand` lists every bundle registered under each. The release gates (`verify-dist-app`, `verify-dist-dmg`) are told `BUNDLE_ID` too, and refuse a signed app under any identifier but the app's own, so a stand's build cannot be published.
- **A dev app is not a stand.** A change to the window is looked at on the operator's own fleet with `make dev-app`: a bundle under `dev.fleetdeck.dev` on a port of its own, which stops no process but its own panel and never updates. See [`dev-app.md`](dev-app.md).
- **A window is visible.** Anything that opens a window, takes a screenshot or steals focus happens on the operator's screen. It needs a moment he agrees to. Afterwards, check that nothing is left open before saying the screen is free.
- **Key presses into the window from another process** (the red button, Cmd+Q) need a permission prompt on the operator's screen. They were not scripted. To the panel, Cmd+Q and SIGTERM to the window are the same event.

## Cleaning up test processes on a shared machine

Several sessions run `go test` on the same machine at the same time. Every run of a package's tests is a binary with the same name: `supervisor.test`, `fleetdeck.test`.

On 2026-09-11, a script written to count stand-in panels left behind by tests matched every process named `supervisor.test`. It killed what it found with `kill -KILL`. Between 15:23 and 15:35 it may have killed a neighbouring session's test run. The session that wrote it found this itself, while reading its own script back. Its report to the orchestrator opened with the harm, before any explanation or fix.

What it taught:

- **A name tells nothing about whose a process is.** A test binary's name is shared by every session testing the same package. Nothing in `ps` output separates your run from a neighbour's.
- **Count by a sign only your process has.** Stand-ins can be told apart: a test binary run again with no arguments (how `StartPanel` and the tests start them), or a copy of it inside a `t.TempDir()` path. A `go test` run always carries `-test.*` flags, so it never matches. A stand panel from a rig is `…/T/Test<Name><digits>/<n>/…/fleetdeck`.
- **Print, do not kill.** The counting script prints PIDs and stops nothing. Stopping is done by hand, by exact PID, after looking at each: its parent (1 for an orphan), its age, its path. The costs are not symmetric. A stand-in left for a minute costs a little memory; a neighbour's killed run costs their work and your credibility.
- **Fix the cause, not the count.** Stand-ins were left because they run in a session of their own, and a test binary killed by its `-timeout` runs no `t.Cleanup`. Each stand-in now watches its test process and exits when it is gone (`watchOwner` in `internal/supervisor/process_test.go`). So does the shell that stands in for the window in `cmd/fleetdeck/owner_test.go`. When the update rig built its stand-ins' environment by hand, it skipped that watch and left eleven panels after one mutation run. Every stand-in now goes through `helperEnvFor`.
- **Prove the fix with both ends.** The fix was measured by killing a test binary by its timeout mid-test, once before and once after. Before, one panel was left; after, none. A zero from a run where nothing was killed proves nothing.

## First launch: the setup surface

A panel whose configuration file does not exist serves the setup page (`internal/server/setup.go`, `web/setup.html`) instead of the panel, and becomes the panel once a workspace is made. Facts from building it, each marked as measured on a stand, read in code, or decided:

- **Decided: only a missing file is a first launch.** A file that exists and does not parse is an error, as it always was. A page that offered setup over a broken configuration would be a way to overwrite somebody's file from a browser.
- **Decided: one listener, one handler, replaced once.** `serve` in `cmd/fleetdeck/main.go` binds, serves the setup surface through `switchHandler`, and after setup loads the new configuration and swaps the panel in. The window watching the port sees no gap and restarts nothing. **Measured:** on a stand the board was on screen 311 ms after Create was clicked, and `/` was answered 200 twice (the setup page, then the panel), never 304.
- **Read, not measured: the setup page carries no ETag, and `Cache-Control: no-store`.** The panel's own page at the same `/` is tagged with the build's web hash and `no-cache`. A stored setup page carrying a validator would be revalidated on the reload after setup, and a matching tag would bring back a 304 and the setup page. The control that was measured is a different one: a build that never swaps the panel in makes the stand's drive stop at the board. So the drive can see a handover that did not happen.
- **Decided after a mutation found it: the configuration is written after the board.** Written first, a board that could not be made left a configuration pointing at nothing, and `init` — which never rewrites a configuration it finds — then refused the corrected path. The page could not recover from its own failure.
- **Read: `os.Rename` on Unix refuses to replace an existing directory, even an empty one,** although `rename(2)` would. `internal/workspace` builds a board in a staging directory beside its place and removes an empty target first. `os.Remove` removes only an empty directory, so a file that arrived in between fails the call rather than being lost.
- **Read: `ServeMux` rejects `GET /` next to `/api/`** (neither is more specific than the other), and panics at registration. The setup surface registers `/` and refuses other methods itself.
- **Read: webview_go calls a bound function synchronously, on the main thread, from WebKit's message handler.** `chooseFolder` (`cmd/fleetdeck-window/choose_darwin.go`) runs `NSOpenPanel`'s `runModal` right there. **Not measured:** the chooser has never been opened. It shows a window on the operator's screen, which needs their go-ahead.
- **Measured: a board made on a machine with no git configuration commits under an identity git makes up** — the account's full name and `user@host.local` — and unsigned. That is what a person who has never configured git gets; the panel adds nothing of its own.
- **Decided: the icon ships twice, and a test holds the copies together.** The drawing lives in `cmd/fleetdeck-window/icon-source.svg` (dark) and `icon-source-light.svg` (light); only the dark one is built into the `.icns` (`scripts/build-icon.sh`, `make icon`). The light variant had no use in the repository until the start page: `web/embed.go` embeds `web/` and nothing above it, so the page cannot read either file, and `web/js/icon.js` carries both as markup. Both are inlined and `web/app.css` shows one, rather than the page choosing — `auto` is the default theme and follows a system that can change under a page already open. `web/tests/icon.test.js` compares the shapes of the two pairs and fails when one copy is redrawn without the other.
- **Measured, the hard way: making a fleet writes under `HOME` too.** The point below about a first-launch stand needing its own `HOME` is not only about first launch. `POST /api/fleets` runs the same `init` steps, so a stand run with the operator's real `HOME` adds its throwaway folder to `permissions.additionalDirectories` in `~/.claude/settings.json` and rewrites that file as formatted JSON — a hand-ordered one does not come back in its own order. Observed on this machine by pressing the start page's own button on a stand that had been given no `HOME` of its own. A stand that makes fleets needs one exactly as a first-launch stand does; where that is not possible, leave the button alone.
- **Stands.** A first-launch stand has no configuration to carry `server.port`, so it takes `-port`, and it needs a `HOME` of its own, since setup writes the configuration, Claude Code's settings and the board's git history under it. See [`docs/en/configuration.md`](../en/configuration.md). A panel built before this change has no `-port`; a "before" stand of it needs a configuration with only `server.port`, which makes it a configured panel, not a first launch.

## The glass frame

On macOS 26 the window lays glass over the board: the orchestrator and sessions columns are `NSGlassEffectView` panels with web views of their own, and the tabs, the new card button, the theme and the limits are system controls in glass capsules (design: `docs/superpowers/specs/2026-09-14-liquid-glass-window-design.md`). Facts from building it, marked as measured, read or decided:

- **Measured (spike, 26.6.2): glass over a `WKWebView` samples the web content under it.** Glass placed under a transparent web view samples only the desktop. So the board's web view stays the bottom layer and the panels sit above it; the side surfaces are transparent web views over the glass.
- **Decided: three web views on one address.** The board, the orchestrator surface and the sessions surface all load the panel's own page. The window injects `window.fleetdeckHost` at document start, and the page mounts only its own part (`web/js/surfaces.js`). A page without it — a browser tab, an older window — is the three-column panel as before. The surfaces share the board's process pool and website data store, so `localStorage` and the theme stay one.
- **Decided: the frame exists only while the board says it is a panel page.** The board reports `fleetdeckLayout({version: 1, mode: "panel", fleet})`. A page of the window's own (starting, taking over, a failure) takes the frame down, and so does a report of another version. The decisions are a pure controller (`controller.go`) answering with effects; `glasswindow.go` carries them out on the main thread, after the callback that produced them has returned, so a surface is never taken down inside its own delegate.
- **Decided: a surface is sent nothing before its page says it loaded.** Each surface gets the same `pageLoadScript` as the board. Until it reports `panel`, the window neither sends it messages nor evaluates anything in it. A surface's page is waited for and asked for again by the board's rules above: each surface has a page watch of its own (`pageWatch`, `navscreen.go`), its navigation delegate reports what WebKit says, and the window's ticker drives both. After `pageLoadTries` in a row the frame goes and the board shows the failed-load page; a surface's web content process lost again soon after a reload takes the frame down with the page saying the panel's page keeps falling. The frame moves the board out of the window's content view, so the board's navigation delegate is set on the board itself.
- **Decided: a surface stays on its page.** Its navigation delegate lets through only its own address. Another page of the panel opens in the board; another site opens in the system browser; other schemes go nowhere (`navigation.go`).
- **Decided: no glass container over the window.** A view over the whole board takes its clicks: hit-testing stops at the deepest view under the pointer, whether or not that view handles the click. The panels are separate glass views directly above the board. The capsule row is one `NSGlassEffectContainerView` the size of the row, so neighbouring capsules merge; the frame's own views and the row pass a click through where no subview of theirs is under the pointer. **Measured in tests** on hidden windows: a click in the capsule row's gap reaches the board.
- **Measured in tests: AppKit swaps an observed view's class.** The glass view reports `NSKVONotifying_NSGlassEffectView` as its class, so the frame asks `isKindOfClass:` instead of comparing names.
- **Measured in tests: glass keeps the clicks on its own content view.** A web view given to `NSGlassEffectView` as its content is drawn, but a click on it lands on the glass. Glass does not size that content view either. So the view a surface's web view goes into lies in the root view directly over its panel, with the panel's frame and an 18 pt rounded layer; the transparent web view still shows the glass, and the glass the board. A hit test on a hidden window pins it: a click in a panel reaches its web view.
- **Decided: a narrow capsule row compacts instead of overlapping.** v0.10.0 laid the capsules out from both edges and never checked that they met: in a 1000 pt window with both panels unfolded the row was about 246 pt, and the right group ran over the tabs, which showed as white empty pills in the dark (CI run 34854756877, macOS 26). That runner drew the frame opaque (see "the runner had been drawing the frame opaque" below): the overlap is geometry and holds in glass too, and the white was the opaque capsules' colour. The row now takes the widest of three forms that fits: every limit with its indicator and the theme's label; the limits as one capsule of text coloured as the worst of them, and the label; that capsule and the theme's icon. The tabs and the new card button stay whole, and the limits are never hidden, since the window has no other place for them. The row is placed again on every change of its width, because a window resize lays the frame out without drawing the capsules again (`capsules_darwin.c`).
- **Decided: the frame keeps the row its narrowest form.** Its width is measured from the drawn capsules' fitting sizes. Where the panels at their widths leave less, the unfolded ones narrow on screen, in proportion, no further than 220 pt; the widths a person set are neither changed nor saved, and a wider window gives them back. A panel's edge dragged in a narrow window stops at the same limit. The window's minimum content width is both panels at 220 pt, the margins and the row's gaps, plus that form; a window narrower than it grows to it when the row is drawn, no wider than the screen's visible frame. **Measured in tests** on hidden windows with the Russian labels: the form is 430 pt, the window's minimum about 908 pt, and no two capsules overlap at 1440, 1000 and 800 pt with the panels unfolded or folded. **Measured on the macOS 26 stand, then fixed:** the board's layout decides the frame before the surfaces draw the row, so the geometry that followed the row's narrowing put the panels back and left the row at 246 pt. A geometry laid out that is no longer the frame for the window as it is now is followed by the current one (`controller.laidOut`), whatever order the effects run in; `capsulestand_darwin.go` drives that path in a test.
- **Measured on the macOS 26 stand: the runner had been drawing the frame opaque.** Until 14.09 21:29 the `window-on-macos-26` screenshots were taken opaque, not in glass, because the runner had `reduceTransparency=1`, and `currentGlassMode` draws the frame and the capsules opaque then. The job now turns reduced transparency and increased contrast off for its stands (`defaults write`, which takes effect in the running session) and puts them back after the tests, and the window's log names the frame's mode and the capsules' material.
- **Decided: every capsule takes the theme chosen in fleetdeck, whatever the system's.** Opaque, a capsule's background (`controlBackgroundColor` taken as a `CGColor`) was resolved in the system's appearance while its controls took the app's: white text on a white capsule with the system light and the app dark, dark on dark the other way (runs 34863293838 and 34864709919). On real glass a capsule's tint came from the board under it, that is the app's theme, and controls drawn in the system's mode instead were unreadable both ways (run 34868250061). The window's log now says the system's appearance as AppKit draws the app before the app is given a theme of its own (`fd_window_system_appearance`, said from `applyAppearance`), and a stand with `FLEETDECK_STAND_SYSTEM` fails unless that is the mode it set. The job also prints what System Events says of dark mode after setting it.
- **Decided: a panel's width is dragged at its edge, by the window.** An 8 pt strip (`FleetdeckResizeStrip`) sits over each unfolded panel's inner edge, with the resize cursor. The frame is laid out again on every drag, in the window's process; the board is told its new insets on release, since each is a layout of the whole board in its web view and the glass shows the board under the panel meanwhile. The width stays between 220 pt and 60% of the window and is kept in the app's defaults on release. The page's own strip (`col-grip`) is hidden in the surfaces and stays for a browser tab.
- **Checked in CI: the frame on macOS 15.** `window-on-oldest-macos` starts this build's window with `scripts/ci-window-stand.sh … frame`: the stand configures a fleet with an empty board and opens the window on `/?fleet=stand`, since `/` is the start page and only a fleet's page reports the layout the frame follows. ## Measuring before trusting

The constants above come with the numbers they were derived from, in the code, next to them. A threshold without its measurement is a guess somebody will copy. Some habits that saved time here:

- **A control case for every measurement.** The swap watch counts gaps during two-step replacements as well. A reader that never saw a gap would otherwise look the same as a swap that never has one.
- **Mutation testing needs two numbers:** how many mutations survived, and how many new tests no mutation failed. The second catches a test that passes whatever the code does. When the harness cannot attribute a kill — a test whose own process the mutation signals, or a Go test of names in a JavaScript file — it is confirmed by hand, without the mutation and with it.
- **Reproduce the whole CI order before pushing:** `go mod verify`, `govulncheck`, `make lint`, `make test`, `make build`, `make verify-ldflags`, `make test-web`, and the docs parity check. Run Linux in a container too, once more with `lsof` installed, so the tests that need it run rather than skip.
