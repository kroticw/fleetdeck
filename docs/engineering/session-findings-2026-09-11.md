# Session findings, 2026-09-11: field notes

This page does not belong to one subsystem the way [window-and-panel.md](window-and-panel.md) and [live-terminal.md](live-terminal.md) do. It is what one session working across this codebase on 2026-09-11 found out the hard way -- the statusline and its local rate-limits file, a concurrency bug and how it was actually reproduced, the column-resize generalization, stand isolation from a live daemon, the macOS app icon, and a broken browser tool worked around -- written down so the next session does not have to rediscover any of it. Everything below is either a mechanism still in the code today or a technique that worked and is worth reaching for again.

## The statusline / local rate-limits file

Claude Code already hands every session's statusline command the account's rate-limit windows on stdin -- a source the panel itself has no way to reach over the network. `cmd/fleetdeck-status` is a thin wrapper installed as the operator's actual `statusLine.command`: it passes stdin through unchanged to whatever the operator's own statusline tool is (`-wrap`, or `statusline.wrap` in `config.yaml`), and separately, best-effort, captures the `rate_limits` object from the same payload and writes it to a local file (`internal/usage`, atomic same-directory temp-file-plus-rename so concurrent writers never leave a half-written value). `cmd/fleetdeck` reads that local file first every cycle and only falls back to the network endpoint if it does not exist yet; the snapshot records which source actually answered, because a two-minute-old local file (nobody's session has ticked recently -- normal) and a two-minute-old network answer (the endpoint itself degraded) look identical by age alone and mean different things to an operator.

Three properties worth remembering if this is touched again:
- The pass-through to the wrapped command always happens first and cannot be affected by anything after it -- reporting to the panel and writing the rate-limits file are both best-effort. A missing wrapped command, one that exits non-zero, and an unwritable rate-limits path all still produce a status line; proven with three end-to-end tests against the actual compiled binary, not mocks.
- `-wrap` is a flag, not an environment variable, because Claude Code (including from Claude.app) runs the statusline command without the operator's shell environment -- a value that had to travel through env would fail silently, invisibly, on exactly the machine that matters.
- The panel shows a rate-limits gauge as stale once the local file is older than two minutes, not only on a hard read error (`isUsageStale` in `web/`) -- an aged-but-error-free file must not read as fresh just because nothing threw.

## Why a wrapper must never default its own output path

`cmd/fleetdeck-status` originally wrote to an implicit default (`~/.config/fleetdeck/rate_limits.json`) when `-rate-limits-path` was not given. The process has no way to tell a real Claude Code invocation apart from a person or script running the binary by hand just to look at its stdout: both present as a piped, non-terminal stdin and a captured, non-terminal stdout, and a realistic test payload is indistinguishable from a real one by content alone. That default caused two real incidents in one evening on this machine -- a hand-run check made purely to inspect stdout silently overwrote the operator's real rate-limits file, once serving synthetic numbers on the live panel for about twenty seconds before anyone noticed.

Fixed by requiring the path explicitly (`-rate-limits-path` or `statusline.rate_limits_path` in config, mirroring `-wrap`'s own precedence): nothing is written when neither is given. A payload that does carry rate-limits data while nothing is configured leaves a line in the trace log rather than a silent no-op -- so upgrading this binary without updating the configured path is a fact someone can find later, not a value that quietly stops moving with nothing on record to say why. The general shape: **a tool that cannot distinguish "really being used" from "being poked to check" must not default to writing anywhere at all.**

## The rate-limits trace log: real concurrent processes catch what goroutines don't

The trace log the fix above added turned out too loud with a real, persistent cause in place: one line every ~15 seconds, unbounded -- 68 lines in seventeen minutes on a real machine, projecting to thousands a day. `AppendTraceOnce` replaced the plain append: a repeated cause writes its one opening line and then stays silent, only counting; a change of cause (including recovery) closes the open streak with one summary line naming how many times it fired and over what span. State persists beside the log in a small JSON sidecar, since the reporter has no memory of its own between runs.

The interesting part is how the concurrency bug in that mechanism was found and proven. `cmd/fleetdeck-status` runs fresh on every session's statusline tick, often several sessions at once on a real machine -- and the trace state's read-check-write was not safe under that. **Tested with real OS processes, not goroutines**, because that is how this binary actually runs in production and a goroutine-based test would not reproduce the same race at all: 20-50 real concurrent processes calling `AppendTraceOnce` with the same cause wrote 2-3 opening lines instead of 1 -- exactly the dedup the file exists to guarantee, broken. Fixed with `acquireStateLock`, a short-lived `O_EXCL` lock beside the state file: a handful of brief retries covers realistic near-simultaneous ticks, and a lock left behind by a process that crashed mid-update is treated as stale after a couple of seconds rather than honoured forever. Losing the race after every retry is not escalated into an error -- the update is simply skipped, and a real cause is seen again on the next tick. **If a race is suspected on code that several real processes touch concurrently in production (not several goroutines in one process), reproduce it the same way: shell out to N real copies of the binary, not N goroutines calling the same function.**

## Generalizing near-duplicate column code, and proving the old side still works

`web/js/columnwidth.js` (fold/resize state and persistence) and later `web/js/columnresize.js` (the drag handle and the CSS side of it) started as the orchestrator column's own code and were generalized to serve the session list too, rather than copied. The reasoning that made copying the wrong call: two near-identical implementations drift apart on the very next edit to either one, in a way no test catches, because nothing ties them together once they're separate files.

The generalization went through a `side` parameter (`"left"` / `"right"`) rather than two code paths, on both the resize arithmetic (`widthPercentFrom`, a pure function so the sign of the drag direction is provable by a table of numbers, not by eyeballing a browser) and the DOM/CSS side (`mountColumnGrip` inserts the handle before or after the column root depending on `side`; `.col-size-left` / `.col-size-right` carry opposite `justify-content`). The generalization also touched persisted state -- storage keys, `data-folded` attributes -- which meant **backward compatibility had to be proven with a test pinned to the literal old string keys**, not just "the new code reads what the old code wrote" by inspection: a test that seeds storage with the pre-refactor key names and asserts the post-refactor code produces the same `--col-width`/`data-folded` output. Renaming a storage key silently would have reset every operator's saved column widths on the next load, with no error and no sign anything had changed except a UI that quietly reset itself.

## Isolating a test stand from a live fleet's real daemon

A panel started anywhere near a running fleet finds the real `fleetd` daemon whether it wants to or not: the daemon's control socket is discovered by globbing `/tmp/cc-daemon-<uid>/*/control.sock` -- keyed to the OS user, not to any per-instance config -- so a separate `--config`, a separate `HOME`, a separate board directory do nothing to isolate a stand from it. A stand accidentally attached to a live daemon can list real sessions (`list` needs no auth key), read real screen content into its own snapshots and logs, and -- worse -- resize a real session's PTY just by opening it in the stand's UI (`attach` needs no key either, only `cols`/`rows`, applied immediately). It cannot write into a session (that needs the control key from `~/.claude/daemon/control.key`, absent under a substituted `HOME`), which is the one thing that made this safe to run at all before it was fixed.

The fix (`--stand-socket`) is a structural guarantee, not a runtime check: `daemon.New(path, key)` and `daemon.Discover(key)` share zero code, so there is no line where a "not found here, fall back to the real one" branch could even be written without rewriting the function that calls it. Given a socket path, the panel only ever dials that path; discovery is never invoked at all in that branch. A path given but empty (`--stand-socket=`, e.g. a templated variable that resolved to nothing) is a hard startup error via `flag.Visit` (which can tell "flag passed with nothing in it" apart from "flag never mentioned" -- a plain `== ""` check cannot), not a silent fall-through to the real daemon. Verified against a real running daemon on this machine with an actual before/after count, not reasoning: 5 real live sessions visible before the fix, 0 after, with a clear `daemonError` naming the unreachable path.

## Getting a real screenshot when the browser automation tool is broken

The `claude-in-chrome` MCP tool's page-content operations (`get_page_text`, `find`, `screenshot`) can go dark independently of anything in this repository -- confirmed by the same failure reproducing on a freshly loaded `https://example.com` in a brand-new tab, with `read_console_messages` on that same tab working normally throughout (whatever breaks lives in resolving frame/page content specifically, not the browser connection as a whole). When that happens, there is still a way to get a real, live check of a UI change without the tool:

1. Build and run the panel on a **spare port** (e.g. `7779`, never the operator's real `7777`), so nothing about the check risks the live instance.
2. Exercise the real HTTP surface directly -- `/api/snapshot` on that spare instance returns exactly what the frontend renders from, so a plain HTTP client (`curl`, or a Node one-liner) against real data proves the backend side without needing a rendered DOM at all.
3. For the frontend logic itself, a direct Node run of the actual module against that same real data (not a browser, not a mock) exercises the real code path headlessly.
4. Where the two above cannot reach (does a human actually perceive an arrow as pointing the right way, is a grip visually graspable) -- say so explicitly as an unverified claim rather than asserting it. A measurement that reports an element as "present, 19x30px" is not the same claim as "a person reads this as a button"; conflating the two has bitten this project before (a return arrow from a collapsed column measured as present and sized while a human read it as pure decoration).

This is a workaround for a tool defect outside this repository, not a fix -- verify the tool is actually broken (reproduce on a neutral page) before reaching for it, rather than assuming every failed browser call needs this detour.

## "What might be affected" is a hypothesis, not "what I tested"

`go build`/`go vet` reporting clean with no `.go` files in a diff is not the same claim as "the Go test suite still passes." `internal/server/static_test.go`'s `TestEmbeddedFSContainsExpectedFiles` checks the exact file list `go:embed` bakes into the binary -- it is a Go test, and it fails on a change to `web/js/*` alone, with zero Go source touched. This has actually broken CI twice on real PRs from a diff that looked, by file extension, entirely outside Go's reach. The general shape: the boundary of "files I changed" and the boundary of "what the test suite actually exercises" are different things whenever anything in the suite cuts across layers (an embed manifest, a generated file list, anything counting a set rather than checking one function's behavior) -- and the second boundary is always the one that decides whether CI is green. Run the real suite before claiming it is unaffected; "I didn't touch X" is a hypothesis about what changed, not a fact about what was verified.

## Building the macOS app icon

`cmd/fleetdeck-window/icon-source.svg` (the dark, outlined variant actually used) and `icon-source-light.svg` (kept as a future source, not wired into the build) are rasterized by `scripts/build-icon.sh` into a full 10-image iconset (16/32/128/256/512, each at 1x and 2x -- a partial set gives a blurry icon in whichever UI surface picks a size that's missing) via `rsvg-convert` + `iconutil`, producing the committed `cmd/fleetdeck-window/icon.icns`. This is a deliberate one-way build, not a CI step: `rsvg-convert` is a Homebrew package present on a developer machine and absent from GitHub's runners, and a build step that silently degrades to a missing or blurry icon on CI would be worse than one that simply does not touch it there. `make icon` is a human-run target that regenerates and re-commits the `.icns` after an edit to the source SVG; `make window-app` only copies the already-built `.icns` into `Contents/Resources` and declares it via `Info.plist`'s `CFBundleIconFile` -- it never invokes the rasterizer.
